Review done — I read all of the integration code (binary_sensor.py, light.py, config_flow.py, init.py, const.py) plus the tests. The overall architecture is solid, but I found several real bugs. One environment note first: I couldn't run the test suite because the .venv is broken — its python symlink points to a deleted Intel Python at /usr/local/bin/python, and the compiled packages (bcrypt, etc.) are x86_64 builds that won't load under arm64 Python. You'll want to recreate it: rm -rf .venv && python3.13 -m venv .venv && .venv/bin/pip install -r requirements (or however you set it up).

Bugs, most impactful first
1. Attribute-only updates silently advance latest_occupied_time forever. async_track_state_change_event fires on attribute changes, not just state changes. In binary_sensor.py:108-122, every event while the real sensor reads "off" recomputes candidate = now - timeout, which is always later than the stored value, so it always wins. Real motion sensors routinely push battery/lux attribute updates while idle — so latest_occupied_time keeps creeping forward in an empty room. Downstream, _compute_occupancy_countdown then believes occupancy was recent, and the illuminance-goes-dark path in light.py:294-300 can turn lights on in an empty room at dusk. Fix: bail out early when old_state exists and old_state.state == new_state.state. The same guard is needed in the combined sensor's handler and in the light's _handle_state_change.

2. The light's own "on" echo clobbers computed countdowns. When illuminance goes dark with recent occupancy, light.py:294-300 enters COUNTDOWN with a carefully computed short timer and turns the real lights on. That turn-on echoes back as a state event: _on_light_state_change sees "on", calls _transition_on, which sees the state is neither OCCUPIED nor ACTIVE — so it flips to ACTIVE and restarts the timer at the full light_timeout, discarding the computed remainder. You need to distinguish self-initiated changes from external ones; the idiomatic HA fix is to create a Context, pass it to async_call in _set_lights, and ignore events whose event.context matches.

3. The virtual light shows "off" in the UI for the whole occupied period. In light.py:242-254, _on_occupancy_change calls async_write_ha_state() while _attr_is_on is still False (the _set_lights(True) task hasn't run yet). _set_lights later sets _attr_is_on = True but never writes state, and the light-on echo takes the early-return path in _transition_on (OCCUPIED) without writing either. Nothing publishes the "on" state until occupancy clears. Fix: set _attr_is_on = True before writing in the handler, or have _set_lights call self.async_write_ha_state().

4. unavailable/unknown is treated as a real reading everywhere. All handlers test state == "on", so a sensor blipping to unavailable (network hiccup, battery swap) reads as "occupancy cleared" — recording a latest_occupied_time and starting countdowns. Worse, the illuminance sensor's _update_from_state sets is_on = False (= dark) when float() fails, so an unavailable lux sensor reads as "dark" and can let lights turn on in broad daylight. Filter STATE_UNAVAILABLE/STATE_UNKNOWN in every handler, and have the illuminance sensor hold its last known value instead of defaulting to dark.

5. Illuminance semantics contradict your own design docs. const.py:39 and idea.md say ON = below threshold (dark), but the implementation at binary_sensor.py:274 is is_on = value >= threshold (ON = bright). The code is internally consistent (light.py treats ON as bright, and device class light conventionally means "light detected"), but the docs describe the inverse. Reconcile one way or the other before it bites a future edit.

6. The core config-flow validation is still a TODO. config_flow.py:270 never enforces light_timeout ≥ occupancy_timeout, which the countdown math depends on — at the moment occupancy clears, the countdown is light_timeout − occupancy_timeout, so a violation means lights snap off instantly. idea.md calls for enforcement in both directions (also when editing an occupancy sensor's timeout upward after lights reference it), and neither direction exists.

7. Entity pickers are too permissive. The light's occupancy/illuminance/schedule selectors (config_flow.py:293-307) filter only on integration=DOMAIN, so you can select a Limer light as your occupancy entity, or an occupancy sensor as your illuminance entity. Add device_class filters (and domain="binary_sensor").

Smaller issues
Bright-at-startup seeding gap: _seed_state returns immediately when illuminance is bright, so if real lights are on at startup they're never adopted — no timer, virtual light shows off, and per your gating rules they arguably should be turned off.
Combined sensor startup heuristic: binary_sensor.py:168-182 lets a maintain-only sensor start occupancy after a restart if it's been on for more than 5 seconds — contradicting "maintain sensors never start." If that's a deliberate restart compromise, document the 5-second constant.
Timer cancellation race: _run_timer only catches CancelledError around the sleep; a cancel landing mid-_set_lights can turn off some lights and abandon the rest.
State is lost across restarts: latest_occupied_time and the turn-on attribution timestamps vanish on restart. Consider RestoreEntity so the occupancy math survives a reboot.
Options-flow rename doesn't stick: the title= argument in an options flow's async_create_entry is ignored, so renaming via options never updates the config-entry title shown in the UI.
Improvements
Replace asyncio.sleep timer tasks with helpers.event.async_call_later. This is the idiomatic HA pattern, it sidesteps the startup-delay problem you patched around with the EVENT_HOMEASSISTANT_STARTED deferral in light.py:129-161, and it makes timers testable by fast-forwarding time. Right now test_light.py:52 does a literal await asyncio.sleep(61) — a real 61-second wall-clock wait per run. With async_call_later you'd use async_fire_time_changed and the test completes instantly.
One service call instead of N in _set_lights — light.turn_on accepts a list entity_id, which is faster and atomic-ish (also fixes the partial-turn-off race above).
Use dt_util.utcnow() instead of datetime.now(timezone.utc) (HA convention, mockable in tests), and BinarySensorDeviceClass.OCCUPANCY/.LIGHT enums instead of raw strings.
The schedule entity is watched by the light but has no branch in _handle_state_change — fine while gating is TBD, but the subscription is currently dead weight.
The schedule sensor polls every minute; computing the next window boundary and scheduling exactly one callback would be cleaner, and datetime.now() there should be dt_util.now() to respect HA's configured timezone.
Dedupe trigger + maintain before subscribing in the combined sensor (a sensor listed in both gets double events).
hass.data[DOMAIN][entry.entry_id] is written in init.py:13 but never read — drop it or use it.
